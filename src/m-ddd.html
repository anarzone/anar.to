At talentsconnect I brought Domain-Driven Design into a legacy PHP codebase, so the business rules could be tested on their own. Here is DDD in three moves, on a made-up recruitment app: put code in the right layer, pick the right building blocks, then split the business into parts that talk through events.

Move 1 · Every class in its layer

Pick a class, then the layer it belongs in.

Every arrow points at the domain. It depends on nothing, so a test of a hiring rule needs no database, no HTTP and no framework.

Move 2 · Same thing, or not?

The aggregate guards the rule

A client is invoiced once per hire. Hire the same candidate twice:

final class Application
{
    public function hire(): void
    {
        if ($this->status === Status::Hired) {
            throw new CandidateAlreadyHired($this->id);
        }
        $this->status = Status::Hired;
        $this->record(new CandidateHired($this->id, $this->jobId));
    }
}
